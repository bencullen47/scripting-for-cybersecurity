## Exercise 3.2 / 3.3

$ ./check_ip.sh case/logs/auth.log 203.0.113.999
NOT FOUND: 203.0.113.999 does not appear in case/logs/auth.log
exit:3

$ ./check_ip.sh case/logs/missing.log 203.0.113.10
Error: 'case/logs/missing.log' not found
exit:2

It makes sense for 'not found' to be a different exit code from 'error' because a missing file is a failure to read the target, while a valid file that simply contains no match is a legitimate negative result. A caller can distinguish a search that returned no hits from a broken or missing input source.

## Exercise 3.4

$ grep -c "203.0.113.1" case/logs/auth.log
18

$ ./check_ip.sh case/logs/auth.log 203.0.113.1
NOT FOUND: 203.0.113.1 does not appear in case/logs/auth.log
exit:3

`grep -c` counts any substring match in the log, so '203.0.113.1' is found inside longer addresses such as 203.0.113.10 and 203.0.113.15. The `check_ip.sh` script uses `grep -qwF`, so it matches only the exact IP as a whole word.

## Answers to challenge questions

1. 198.51.100.77 made 8 failed login attempts. It is not in the IOC list and it is not in the firewall log. This shows that an IOC list alone can miss active attackers or newly observed addresses, so it should be used as a lead rather than the only source of truth.

2. 203.0.113.200 is in the IOC list. The firewall blocked it to port 3389, which is the default port for RDP (Remote Desktop Protocol). In auth.log it is attacking SSH (the log lines show 'port 51029 ssh2'), so the firewall is blocking the RDP service, while the auth log shows SSH credential attacks.

3. 203.0.113.77 appears in the web log but not the auth log. The requests include GET /admin, GET /assets/app.js, GET /wp-login.php, and /index.html, with some 403 and 200 responses and a tool signature such as 'sqlmap/1.8' or 'curl/8.4.0'. That is consistent with web probing and enumeration of admin/login paths rather than SSH login activity.
